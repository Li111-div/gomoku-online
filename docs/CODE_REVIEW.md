# 代码审查标准与流程

> 配套文档：[`CODE_STYLE.md`](./CODE_STYLE.md)（写代码的规范） · [`REVIEW_CHECKLIST.md`](./REVIEW_CHECKLIST.md)（逐项自查清单）
> 配套工具：`tools/preflight.py` + `preflight.bat`（自动化门禁）

---

## 0. 先诊断：质量为什么会参差不齐

在定标准之前，先说清楚问题出在哪。多数团队的情况是这四条：

| 症状 | 真实原因 |
|---|---|
| 同样的低级错误反复出现 | 靠人眼查机械问题 —— 人会累、会漏、会讲情面 |
| 规范写了没人看 | 标准太抽象（"代码要清晰"），无法判定是否达标 |
| 有人认真、有人敷衍 | 没有门禁，全靠自觉；遵守成本高于收益 |
| 不知道哪里在退化 | 没有度量，问题暴露时已经积重难返 |

**结论：质量参差不齐的根因不是"标准缺失"，而是"标准不可执行"。**

所以本文的重点不是再写一份更长的规范，而是建立一套**能被强制执行、能度量、能自我修正**的机制。

---

## 1. 三条原则

### 原则一：机器能判断的，绝不交给人
缩进、语法、未使用的变量、选择器写错、常量两边不一致 —— 这些**不该占用人的注意力**。
全部交给 `preflight.py`，人只负责机器判断不了的部分：设计是否合理、边界是否覆盖、逻辑是否自洽。

> 经验值：一次代码审查中，约 **60% 的意见本可以被自动化检查提前拦下**。把这 60% 交给机器，人工审查的效率会翻倍，而且审查者不容易疲劳。

### 原则二：每条标准必须可判定
不能判定的标准等于没有标准。

| ❌ 不可判定 | ✅ 可判定 |
|---|---|
| 代码要写得清晰 | 单个函数不超过 50 行；嵌套不超过 3 层 |
| 命名要合理 | 布尔变量用 is/has/can 前缀；私有成员用 `_` 前缀 |
| 注意性能 | 渲染必须走 requestAnimationFrame；禁止在循环内查询 DOM |
| 要有错误处理 | 每个异步链必须有 `.catch`；空 catch 必须写注释说明原因 |

### 原则三：门禁宁松勿严，但定了就不许绕过
门禁太严 → 大家想办法绕过去 → 机制失效。
所以只把**确定无误、零误报**的规则设成阻塞项（ERROR），其余设为提示项（WARN）。
但一旦成为 ERROR，**任何理由都不能绕过**（紧急修复也走同样流程，见 §8.3）。

## 2. 四层防线

```
   ┌─────────────────────────────────────────────────────────┐
   │  L1  自动化门禁         python tools/preflight.py       │
   │      语法 / 协议同步 / 禁用模式 / DOM 引用 / 架构不变量   │
   │      零依赖 / 文件规模 / 未引用文件                       │
   │      → ERROR 必须为 0，否则不进下一步                     │
   └─────────────────────────────────────────────────────────┘
                            ↓ 通过
   ┌─────────────────────────────────────────────────────────┐
   │  L2  作者自查           docs/REVIEW_CHECKLIST.md         │
   │      59 项可勾选清单，作者逐条过一遍                      │
   │      → 🔴 必须项未通过则不得提交审查                      │
   └─────────────────────────────────────────────────────────┘
                            ↓ 通过
   ┌─────────────────────────────────────────────────────────┐
   │  L3  人工审查           只看机器判断不了的                │
   │      设计合理性 / 逻辑正确性 / 边界覆盖 / 可维护性         │
   │      → 按 P0–P3 分级，P0 必须改                          │
   └─────────────────────────────────────────────────────────┘
                            ↓ 通过
   ┌─────────────────────────────────────────────────────────┐
   │  L4  端到端验证         功能测试全绿                     │
   │      多实例联机 / 服务端权威性 / 多房间隔离 / 响应式       │
   │      → 有失败项则不得合入                                │
   └─────────────────────────────────────────────────────────┘
                            ↓
                         合入主干
```

**为什么要分层？** 因为每一层的成本递增：机器检查是毫秒级、作者自查是分钟级、人工审查是小时级。
让问题在最便宜的那一层被拦下。

### L1：自动化门禁

```bash
python tools/preflight.py       # 或双击 preflight.bat
```

八类检查：

| 检查 | 拦截什么 | 级别 |
|---|---|---|
| 语法 | JS / Python 语法错误 | ERROR |
| 协议常量 | 客户端 `GM.MSG` 与服务端 `protocol.py` 不一致 | ERROR |
| 禁用模式 | `var`、`debugger`、`innerHTML` 拼接 | ERROR |
| DOM 引用 | JS 里引用了不存在的 id | ERROR |
| **架构不变量** | 客户端出现棋局规则（胜负判定、四方向遍历） | ERROR |
| 零依赖 | 服务端引入了第三方模块 | ERROR |
| 文件规模 | 逻辑文件 > 800 行、样式文件 > 1200 行 | WARN |
| 未引用文件 | 没有被加载 / 导入的文件 | WARN |

其中「架构不变量」这一项是**这个项目特有的护栏**：它保证了「棋局规则只存在于服务端」这条设计决策不会被后来者无意破坏。

> 门禁会误报吗？会。第一次运行时它就误报了我自己写的检查规则（`board.js` 只是存储服务端给的 `winLine`，并没有计算）。
> **规则误报要改规则，不要改判定标准去迁就代码。**

### L2：作者自查

`docs/REVIEW_CHECKLIST.md` 共 59 项，分九类（正确性 / 状态同步 / 网络 / 安全 / 性能 / 内存 / UI / 响应式 / 可维护性），每项标了 🔴（必须）或 🟡（建议）。

**自查不是形式**：把"我检查过了"变成"我逐条确认过了"，能挡掉大量本该在审查阶段被指出的问题。

### L3：人工审查

**只做机器做不了的事**。见 §9「审查者该看什么」。

### L4：端到端验证

功能测试必须全绿，包括：多实例联机、服务端权威性、多房间隔离、断线重连、响应式三档。

## 3. 角色与职责

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **作者** | 保证 L1/L2 通过；把改动讲清楚；对审查意见逐条回应 | 不把未自查的代码丢给审查者 |
| **审查者** | 在约定时效内给出分级意见；对 P0 必须说明理由 | 不替作者改代码（除非作者明确请求）；不做纯风格挑刺 |
| **合入者** | 确认 L1–L4 全部通过后合入；对最终结果负责 | 不在门禁未过时合入 |

小团队（2–3 人）可以一人身兼多角，但**作者与审查者不能是同一个人**。

## 4. 问题分级与合入门禁

### 4.1 四级分类

| 级别 | 含义 | 典型例子 | 处理要求 |
|---|---|---|---|
| **P0 阻塞** | 正确性、安全、架构红线 | 胜负判定错误；客户端能作弊；服务端可被异常消息打断连接；`innerHTML` 拼接用户输入 | **必须修复**，无例外 |
| **P1 重要** | 健壮性、性能、可维护性 | 异步链缺 `.catch`；未清理定时器；高频回调未节流；重复代码三处以上 | **必须修复，或在评审记录中写明不修的理由** |
| **P2 建议** | 命名、注释、结构优化 | 变量名不够准确；函数可以拆小一点；补一段注释说明"为什么" | 可延后，**记入待办**，不阻塞合入 |
| **P3 吹毛求疵** | 个人偏好 | 大括号换行位置；`if` 里要不要写 `else` | **不阻塞**，作者有权拒绝 |

### 4.2 合入门禁（全部满足才可合入）

- [ ] L1 自动化门禁：**ERROR = 0**
- [ ] L2 自查清单：所有 🔴 项通过
- [ ] L3 人工审查：**P0 = 0，且 P1 = 0 或已记录不修理由**
- [ ] L4 端到端测试：**全绿**
- [ ] 审查意见已逐条回应（同意 / 不同意并说明理由）

> 注意：**P2/P3 不阻塞合入**。如果把所有意见都设成必须改，审查会变成瓶颈，作者会开始躲审查。

### 4.3 什么情况下可以例外

只有一种：**线上故障紧急修复**。
此时允许先合入，但必须在 **24 小时内补齐**门禁与审查，并在下一次复盘中说明。

## 5. 完整流程

```
  ①  作者本地开发
      │
      ├─► 跑 preflight（ERROR 必须为 0）
      ├─► 跑功能测试（必须全绿）
      └─► 过一遍 REVIEW_CHECKLIST 的 🔴 项
      │
      ▼
  ②  提交审查请求
      │   · 写清楚：改了什么 / 为什么改 / 怎么验证的
      │   · 单次改动控制在 400 行以内（见 §6）
      │
      ▼
  ③  审查者审查（时效见 §7）
      │   · 先看改动意图与整体设计，再看逐行细节
      │   · 意见按 P0–P3 标注
      │   · P0 必须说明「为什么这是阻塞项」
      │
      ▼
  ④  作者逐条回应
      │   · 接受 → 修改并回复"已改"
      │   · 不接受 → 说明理由，进入 §8 分歧处理
      │
      ▼
  ⑤  复审（只审改动部分，不全量重读）
      │
      ▼
  ⑥  合入
      │
      ▼
  ⑦  度量记录（见 §10）
```

**关键点：第 ⑤ 步只审改动部分。** 全量重读会让审查者疲惫，也会拖长周期。

## 6. PR（改动）规范

### 6.1 规模

| 改动行数 | 评价 |
|---|---|
| < 200 行 | 理想，审查质量最高 |
| 200 – 400 行 | 可接受 |
| 400 – 800 行 | 建议拆分 |
| > 800 行 | **必须拆分**（纯移动/重命名除外） |

> 这不是形式主义。研究表明，审查者超过约 400 行后，发现缺陷的密度会急剧下降 —— 后面的代码基本是"扫"过去的。

### 6.2 拆分原则

一次改动只做一件事。以下必须分开提交：

- 重构与功能改动
- 格式化与逻辑修改
- 依赖升级与业务代码

### 6.3 描述模板

见 [附录 A](#附录-apr-描述模板)。**"怎么验证的"是必填项** —— 没有验证方式的改动，审查者无法判断它是否真的可用。

---

## 7. 时效约定

| 改动规模 | 审查者首次响应 | 完整审查完成 |
|---|---|---|
| < 200 行 | 4 小时内 | 1 个工作日 |
| 200 – 400 行 | 1 个工作日 | 2 个工作日 |
| 紧急修复 | 1 小时内 | 当天 |

**超时的处理**：超过约定时效未响应，作者可以找第二审查者，并在复盘时提出。

> 审查时效是机制能否落地的关键。如果提交后三天没人看，作者下次就不会再认真写描述、跑门禁了。

## 8. 分歧与升级

### 8.1 技术分歧

```
作者不同意审查意见
   │
   ├─► 先讨论：把理由讲清楚（为什么这样做更好）
   │      · 达成一致 → 继续
   │      · 未达成  → 下一步
   │
   ├─► 判断级别
   │      · P2 / P3 → 作者有权决定，记录结论即可
   │      · P0 / P1 → 需要第三人（维护者）裁决
   │
   └─► 裁决结果写入评审记录，作为后续同类问题的判例
```

**原则：P0/P1 的分歧不能靠"谁声音大"解决，必须有裁决人和记录。**

### 8.2 规则本身有争议

如果某条门禁规则被反复质疑，说明规则本身可能有问题。处理方式：

1. 在复盘中提出，说明它拦下了什么、误报了什么
2. 用数据决策：如果误报率 > 20%，降级为 WARN 或修改规则
3. **不要私下绕过** —— 绕过一次，规则就失效了

### 8.3 紧急修复通道

线上故障时：

1. 允许先合入（但必须跑一次 preflight，语法错误仍然不能进）
2. 24 小时内补齐完整审查
3. 在下一次复盘说明为什么需要走紧急通道

**紧急通道不是"快速通道"**，用多了就要查原因。

## 9. 审查者该看什么

### 9.1 应该重点看

| 维度 | 具体问题 |
|---|---|
| **设计** | 这个改动放在这一层合适吗？有没有更好的位置？ |
| **正确性** | 边界条件覆盖了吗？空值 / 极值 / 并发 / 断线？ |
| **一致性** | 与现有代码的约定一致吗？命名、分层、错误处理方式 |
| **可维护性** | 半年后的人能看懂吗？为什么这么做有注释吗？ |
| **测试** | 验证方式可信吗？有没有"只测了 happy path"？ |
| **架构不变量** | 有没有破坏核心设计决策（如"客户端不做棋局判断"）？ |

### 9.2 不该花时间看

以下应该由 L1 门禁或 L2 自查挡掉，**如果它们出现在审查意见里，说明前两层没做好**：

- 缩进、空格、引号风格
- 变量命名的大小写规范
- 语法错误、未使用的变量
- 常量两边不一致

### 9.3 提问方式

**不要直接给答案，先问问题。** 有些看起来错误的写法，作者可能有你不知道的理由。

| ❌ 直接否定 | ✅ 提问 |
|---|---|
| 这里应该用 map 而不是 for | 这个循环有特别的原因吗？用 map 会不会更清晰？ |
| 你没处理空值 | 如果 `msg.text` 是 undefined，这里会怎样？ |
| 这段代码太长了 | 这个函数承担了几件事？能拆开吗？ |

## 10. 度量与改进

没有度量就无法改进。每次审查记录以下数据：

| 指标 | 含义 | 健康值 |
|---|---|---|
| **L1 首次通过率** | 提交前跑门禁就通过的比例 | > 80% |
| **P0 数量** | 每次审查发现的阻塞问题数 | 逐月下降 |
| **缺陷逃逸率** | 合入后才发现的问题数 / 总问题数 | < 10% |
| **审查时长中位数** | 从提交到完成审查的时间 | 在 §7 约定内 |
| **P2/P3 占比** | 低级别意见的比例 | 过高说明前两层没做好 |

### 月度复盘（30 分钟，固定议程）

1. 过一遍上月数据，看趋势
2. 挑 1–2 个**缺陷逃逸**案例，问：哪一层本可以拦住它？
3. 如果答案是"L1 可以拦" → 加一条门禁规则
4. 如果答案是"L2 可以拦" → 补充清单条目
5. 如果答案是"只能靠人" → 记录为已知风险，不必强求

> **这个闭环是整套机制能自我进化的关键。** 没有它，门禁会逐渐和实际脱节。

## 11. 分阶段落地路线

一次性推行全套流程会失败。分四步：

### 第 1 周：门禁上线（只警告，不拦截）
- 跑 `preflight.py`，收集基线数据
- 目标是**让所有人知道自己的代码有多少问题**，而不是马上改正
- 预期：会看到一批 ERROR 和 WARN

### 第 2 周：门禁转强制
- 把 ERROR 设为阻塞项
- **先把存量问题清干净**，否则门禁第一天就会被绕过
- 此时 L1 应该达到 100% 通过

### 第 3–4 周：加入 L2 自查
- 作者提交前过一遍 `REVIEW_CHECKLIST.md`
- 先只要求 🔴 项，🟡 项作为后续目标

### 第 2 个月起：加入 L3/L4 与度量
- 人工审查按 P0–P3 分级
- 建立月度复盘
- 开始记录 §10 的指标

> **每一步都要等前一步稳定再推进。** 同时推行四层，等于一层都落不了地。

## 附录 B：审查评论模板

```markdown
【P0·阻塞】<问题描述>
位置：<文件:行号>
理由：<为什么这是阻塞项，会导致什么后果>
建议：<具体怎么改>

---

【P1·重要】<问题描述>
位置：<文件:行号>
理由：<不修的话会有什么风险>
建议：<具体怎么改>

---

【P2·建议】<问题描述>
位置：<文件:行号>
说明：<不阻塞合入，可记入待办>

---

【提问】<问题>
<!-- 不确定是不是问题时的问法 -->
```

**注意**：每条意见都要有「位置」和「理由」。
只写"这里不太好"的意见，作者无法处理，还会产生情绪。

## 附录 C：审查反模式

| 反模式 | 表现 | 后果 | 对策 |
|---|---|---|---|
| **橡皮图章** | 秒回 LGTM | 审查形同虚设 | 记录审查时长，过短的会被复盘关注 |
| **挑刺型** | 只提 P3 风格问题 | 作者抵触，真正的问题被淹没 | 意见必须分级，P3 不超过总数的 20% |
| **自行车棚** | 在无关紧要的细节上争论不休 | 消耗时间，回避了核心设计问题 | 先给 P0/P1 意见，再谈细节 |
| **全量重读** | 复审时把整个文件重看一遍 | 效率低，周期长 | 复审只看改动部分 |
| **延迟审查** | 提交后几天没人看 | 作者失去积极性 | 遵守 §7 时效，超时找第二审查者 |
| **替作者改** | 审查者直接改代码 | 作者不学习，责任不清 | 只提意见，除非作者明确请求 |
| **无记录分歧** | 争论完就过去了 | 同类问题反复争论 | 分歧结论写入评审记录，作为判例 |

```
提交前      python tools/preflight.py        → ERROR 必须为 0
           REVIEW_CHECKLIST 的 🔴 项          → 全部通过
           功能测试                           → 全绿

提交时      改动 < 400 行
           描述写清「怎么验证的」

审查时      先看设计，再看细节
           意见按 P0–P3 分级

合入条件    P0 = 0
           P1 = 0 或已记录理由
           L1 / L4 全绿
```
